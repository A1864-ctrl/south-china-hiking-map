# 野径 · 待优化点与新功能建议

> 2026-11-06 20:59　·　基于当前版本（山友社区 + 一周会话）的实际状态盘点
> 每条都标了「现状问题 → 怎么改 → 预期收益」，按投入产出排序

---

## 一、界面层：现在就能改、收益立竿见影

### P1　首页缺少「一张图说服人」

**现状**：首页是纯文字 + 数字 + 表格，第一次进来的人 3 秒内看不到任何风景。
**改法**：顶部换成一条 21:9 的全宽图带（用已有的 110 张封面里最好的一张，或三张轮播），标题压在图上，下面才是数据。
**收益**：首页跳出率通常能降 20–30%；对答辩演示来说，第一屏观感决定印象分。

### P1　移动端导航缺折叠

**现状**：6 个导航项在 760px 以下靠隐藏副标题和文字硬撑，手机上只剩图标，认不出来。
**改法**：≤760px 改成底部标签栏（5 个常用项）+ 「更多」抽屉，或汉堡菜单。
**收益**：手机端可用性从「能点但认不出」变成正常水平；这是唯一还没解决的响应式短板。

### P2　路线卡与景点卡的信息层级偏平

**现状**：卡片上标题、里程、爬升、难度、标签字号接近，眼睛没有落点。
**改法**：标题加粗到 1rem、数值改等宽字体并放大 0.15rem、标签降为 0.7rem 浅灰。
**收益**：扫读速度提升，列表翻起来不费劲。

### P2　图片缺懒加载的占位

**现状**：`loading="lazy"` 有了，但加载中是空白，滚动时会有跳动（CLS）。
**改法**：给 `figure` 预设 `aspect-ratio`，配一个纯色 / 模糊占位块。
**收益**：滚动更稳，弱网下不出现大片空白。

### P3　深色模式

**现状**：只有浅色。夜晚在山里看路线时刺眼。
**改法**：CSS 变量已经集中，加一套 `[data-theme=dark]` 覆盖即可。
**收益**：户外场景实际有用；实现成本低（变量已就位）。

## 二、功能层：影响正确性与可信度

### P1　会话续期只挂在「我的收藏」页

**现状**：`touch()` 只在 `MeView` 的定时器里调用。你在景点页、路线页翻一小时，会话不会续期。
**改法**：提到 `App.vue`，全局监听 `click / keydown / scroll`（节流 5 分钟一次）。
**收益**：符合「有操作就不掉线」的定义。改成 7 天后影响很小，但逻辑上是个洞。

### P1　社交数据全在本机，换设备就没了

**现状**：帖子、搭子、位置都存在 `localStorage`。换浏览器或清缓存，你发的帖子消失。
**改法**：MySQL 库已经建好（`post` / `buddy_post` / `presence` 表），只差后端 API。
**收益**：从「演示」变成「真能用」。这是当前最大的一块短板。

### P2　附近的人是预置样本，不是真实用户

**现状**：6 个「山友」是写死的演示数据，只有你一个真实账号。
**改法**：接上 `presence` 表 + 浏览器 Geolocation，多设备打开就能互相看见。
**收益**：这个功能目前只能演示交互，不能真用。

### P2　轨迹仍是「走向示意」，不是实测 GPS

**现状**：沿高德瓦片步道追踪生成，与真实轨迹有出入；部分线路里程明显短于标注。
**改法**：接入两步路 / OSM 的 GPX 数据，或让用户上传轨迹补全。
**收益**：可信度提升一个量级。这是唯一会被专业用户一眼看穿的短板。

### P3　搜索没有历史记录与联想

**现状**：输入即筛，但没有下拉建议、没有搜索历史。
**改法**：输入时给前 5 个候选（点位名 / 路线名），本地存最近 10 条搜索。
**收益**：减少打字，提升查找效率。

## 三、新功能建议

### 短期（1–2 天可做，价值明确）

| 功能 | 说明 | 为什么值得做 |
|---|---|---|
| **行程单导出** | 把收藏的路线 + 装备清单导成一张 A4 PDF | 出行前真的要打印；答辩时是加分项 |
| **天气接入** | 路线详情显示未来 3 天天气与日出日落 | 决定去不去的第一因素 |
| **轨迹 GPX 导入** | 用户上传自己的 GPX，覆盖示意线 | 一次性解决轨迹可信度问题 |
| **装备清单分享** | 生成一张可分享的清单卡片图 | 传播性强，适合小红书 |

### 中期（1–2 周，需要后端）

| 功能 | 说明 | 依赖 |
|---|---|---|
| **真账号体系** | 手机验证码 / 微信登录，跨设备同步 | MySQL + Redis（已设计好） |
| **评论盖楼与通知** | 回复、@、未读提醒 | post / comment 表 |
| **搭子聊天** | 同意后开私信，不用跳微信 | conversation / message 表 |
| **路线众包修订** | 用户提交勘误（像岳麓山起终点那种），审核后入库 | 新增 revision 表 |

### 长期（需要团队与运营）

| 功能 | 说明 |
|---|---|
| **离线地图包** | 山区无信号，提前下载瓦片与轨迹 |
| **组队实时位置** | 队伍内共享位置，掉队报警 |
| **AI 行程规划** | 按天数 / 体力 / 预算生成行程，直接落到收藏 |
| **UGC 图库** | 用户上传实拍，按季节与时段归档（替代现在抓来的图） |

## 四、优先级矩阵

```
收益高 ┬  P1 首页图带        P1 社交接后端
       │  P1 移动端导航      P2 轨迹接真实 GPX
       │  P2 深色模式        P2 附近的人接真实位置
       ├──────────────────────────────────────
       │  P3 搜索联想        P3 众包勘误
收益低 ┴  投入小            投入大
```

**如果只有一天**：做「首页图带 + 移动端导航 + 会话续期全局化」这三件，成本最低、观感提升最大。
**如果有一周**：优先把社交接上后端，让帖子能跨设备——这是从「作品集」到「产品」的分界线。

## 五、当前版本已知的取舍（不是 bug，是选择）

| 取舍 | 原因 |
|---|---|
| 社交数据存本地 | 没有后端服务时，这是唯一能让功能「真的跑起来」的办法 |
| 附近的人是样本数据 | 单机演示没有第二个真实用户 |
| 轨迹是示意线 | 拿不到真实 GPX，硬凑里程会变成假锯齿 |
| 图片来自公开渠道 | 抖音 / 小红书需要登录且反爬，无法批量抓取；现有 564 张已逐张核验 |
| 会话 7 天 | 演示环境不需要更严格；真实产品应该 access 15 分钟 + refresh 7 天 |
